## Source ownership and identity

Photographic sources were generated by the project owner with ChatGPT; the owner confirmed deployment rights.

- Use only the seven categories above and meaningful English filenames based on a visual review. Never use SHA-based placeholder names.
- Preserve original bytes, SHA-256 and extensions, including .jfif. Never overwrite an existing source or re-encode it merely to rename it.
- Existing stable Visual IDs survive category moves, theme changes and derivative regeneration. Assign a new ID only to a genuinely new record.
- Archived records remain deploy: false with no runtime variants; exact duplicates cannot enter the deployed pool twice.
- The six frozen images under design/themes/references are separate and immutable.
- Respect intentional user deletions. Do not reconstruct retired assets from historical branches.

## Ingestion workflow

1. Place new sources in inbox/ and inspect each actual image.
2. Review semantic names, categories, tags, source families and suitability in explicit approvals.
3. The ingest tool defaults to dry-run. Use its reviewed apply mode to actually move/rename approved originals into originals/{category}/, update the manifest and generate optimized derivatives.
4. Synchronize the runtime manifest and asset audit/migration records. Run npm run check:visuals and npm run test:visuals; regenerate contact sheets with npm run visuals:sheets.
5. For changed or new derivatives, regenerate the manual upload plan with npm run visuals:storage, upload the prepared files yourself, then run npm run visuals:storage -- --verify --activate.

The [ingest tool](../../tools/ingest-visual-library.cjs) checks conflicts and source hashes. Do not overwrite same-name files or treat a dry-run as completed ingestion.

## Runtime selection and cloud delivery

All 48 reviewed JPEG derivatives were manually uploaded to the public Supabase visual-library bucket and verified against exact MIME, bytes and SHA-256. [Upload plan](storage-upload-plan.json) and [client storage configuration](../../apps/miniprogram/src/visual-storage.json) are verified and enabled. The object layout is {category}/{semantic-name}.jpg.

Chat selection reuses the existing DeepSeek request. The model receives reviewed candidate metadata and returns a stable ID or null; the server validates eligibility and excludes used IDs and source families. The client resolves the ID locally to its approved cloud URL. Theme changes make no extra model call; incompatible or failed chat imagery is hidden. This selects existing library artwork and does not generate new images.

Formal builds exclude only the exact byte-verified cloud copies from generated output. Originals and source derivatives remain intact. Disabling cloud configuration restores local copies on the next build. Never invent a dark variant: an insufficient night pool remains text-only.

See [cloud acceptance and limits](../../docs/visual-library/CLOUD-ACCEPTANCE-2026-10-23.md) and the [visual asset contract](../../docs/VISUAL-ASSET-SYSTEM.md).

## Selection scope

DeepSeek selects optional chat-message artwork from reviewed candidates; it does not periodically rotate all page images. Discover and Plan artwork remain client-resolved, and Discover recommendation rotation is local. Backend filtering uses saved user.theme, which may differ from the frontend automatic time theme. See the [current code audit](../../docs/VISUAL-ASSET-SYSTEM.md#current-selection-ownership--code-audit-2026-10-25) for exact triggers and limitations.

## Packaged image/audio budget — 2026-10-25

WeChat DevTools checks the aggregate size of media in the compiled package, not each file separately. The installed IMAGE_AND_AUDIO_LIMIT implementation sums matching compiled files and requires totalBytes / 1024 < 200 (strictly below 204,800 bytes). Its extension list includes SVG, audio and MP4 as well as raster images. The linked tutorial is https://developers.weixin.qq.com/community/develop/doc/00040e5a0846706e893dcc24256009 . The rule was verified in the installed DevTools implementation because the tutorial could not be fetched.

The initial formal package contained 1,513,449 media bytes even though no individual file exceeded 200K. A further 32 approved presentation/legacy images (1,390,696 bytes) now use verified objects under visual-library/app-media/ without modifying their bytes or overwriting existing objects. apps/miniprogram/src/app-media.json contains their public URLs, lengths, SHA-256 values and verification timestamps. resolveAppMedia handles opening slides and legacy imagery; resolveStoredVisualPath retains its existing visual mapping and uses this exact fallback map. Small controls, avatars, icons and four explicit Discover fallback thumbnails stay local. Lightweight source derivatives remain available to backend validation and maintenance.

The Mini Program Vite writeBundle hook runs after static copying for both development and release builds. It removes only exact verified cloud-backed artifact copies and fails if aggregate media reaches 200KiB. tools/check-mp-media.cjs and the native artifact checker independently enforce the same rule. Unexpected or changed files are not silently removed. Editing a static source while the development static-copy watcher is active can copy it again; rerun a complete build and the budget check before upload.

Both fresh development and release builds measured 131 media files, 183,372 bytes (179.07KiB), below the limit. The release build passed native compilation (38 WXSS, 60 WXML). Focused frontend tests passed 29/29; tool tests passed 24/24; TypeScript passed. Backend visual-selection MockTransport tests and manifest validation passed. These results do not claim physical-device image loading or a fresh UI code-quality-panel scan. Recompile the current project and rerun its code-quality scan; do not reuse a pre-migration result.
